# Monetizing Dashboard — dbt Project

A dbt project modelling a cross-sell monetizing dashboard: partner products
promoted across channels, aggregated at daily / weekly / monthly grain.

Built as a portfolio demonstration of Analytics Engineering practice —
layered modelling, grain-aware tests, and reproducible local runs.
Data is synthetic; structure mirrors a production pipeline.

## Stack

- **dbt-core 1.12** + **dbt-duckdb** — runs entirely locally, no cloud account
- **DuckDB** — embedded analytical database, one file (`dev.duckdb`)
- **dbt_utils** — for `unique_combination_of_columns`

## Quick start

```bash
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
dbt deps
dbt build
```

`dbt build` runs seeds → models → tests in dependency order.
Expected result: `PASS=37 WARN=0 ERROR=0`.

## Architecture

```
seeds (raw_contacts, raw_channels)
   ↓
staging (stg_contacts, stg_channels)        — view
   ↓
intermediate (int_contacts_enriched)         — view
   ↓
marts (daily / weekly / monthly)             — table
```

- **Staging** — type casting, renaming, light cleaning. No business logic.
- **Intermediate** — one model: contacts joined with the channel dictionary.
  Enrichment happens once here, not in every mart.
- **Marts** — aggregation to three grains. Each mart owns its grain and metrics.

## Grain and metrics

| Mart | Grain | Metrics |
|---|---|---|
| `mart_monetizing_daily` | `(day_date, channel, channel_group, product, device)` | `total_contacts`, `unique_contacts` |
| `mart_monetizing_weekly` | `(week_date, ...)` — ISO week, Monday start | same |
| `mart_monetizing_monthly` | `(month_date, ...)` | same |

`total_contacts` = `SUM(contact_count)` — additive.
`unique_contacts` = `COUNT(DISTINCT contact_id)` — **non-additive** across
days/weeks/months. Each grain is aggregated from the enriched event layer,
not from a coarser mart.

## Tests

29 tests total:

- **Generic** — `unique`, `not_null`, `accepted_values`, `relationships`
  on staging; `unique_combination_of_columns` on each mart's grain.
- **Singular** — `assert_monthly_matches_daily`: verifies that monthly
  `total_contacts` equals the sum of daily `total_contacts` per month.
  Catches lost or duplicated months that a grain-level test can't see.

Run just the tests: `dbt test`.

## Reproducibility

Synthetic data is generated by `scripts/generate_seeds.py` with a fixed
random seed — re-running produces identical CSVs.

To regenerate:
```bash
python scripts/generate_seeds.py
dbt seed
```

## Design notes

- **Raw grain is intentionally non-unique.** The same contact can repeat
  (a user re-contacted on the same day). Deduplication happens at aggregation
  via `COUNT(DISTINCT contact_id)`, not in staging.
- **Three grains, not one.** In production the three aggregates could live in
  one table with a `time_period` column for efficiency. Here they are modelled
  as three marts so each grain is explicit and testable.
- **No incremental models.** Data is small and synthetic; full rebuilds keep
  the demo simple. For production volumes, marts would use incremental
  materialization keyed on the grain.

## What's not here (roadmap)

- Incremental marts for production-scale data
- Snapshots / SCD
- Exposures for BI dashboards
- Airflow orchestration (the equivalent DQ checks run in Airflow in production —
  see the [Data Quality Library](../data-quality-library/) case study)
